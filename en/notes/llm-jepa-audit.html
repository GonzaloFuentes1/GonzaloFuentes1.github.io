Auditing LLM-JEPA: the gain disappears once the baseline learns to stop

Gonzalo Fuentes · November 2026 · code, logs and predictions: github.com/GonzaloFuentes1/llm-jepa-sigreg

TL;DR. I reproduced the LLM-JEPA fine-tuning result on NL-RX-SYNTH with Llama-3.2-1B-Instruct (Huang, LeCun and Balestriero, arXiv:2509.14252). The published numbers reproduce with the official code. They come from a padding fallback, pad_token = eos_token, that removes every end-of-turn target from the language-modeling loss. With a dedicated pad token, the baseline goes from 54.6% to 83.7% exact match and LLM-JEPA brings no gain (83.9%, paired p = 0.49). Adding SIGReg from LeJEPA to the JEPA embeddings does not help either. I opened a fix upstream.

The claim

LLM-JEPA adds a JEPA term to next-token prediction. Two views of the same example, the natural-language description and the regular expression, are embedded with the LLM itself, and their last-token embeddings are pulled together with a cosine loss. On NL-RX-SYNTH the paper reports exact match going from 57.29 ± 5.32 to 71.46 ± 1.34 for Llama-3.2-1B-Instruct.

Reproduction

I re-implemented the official training path on one H100 per run, with the same global batch (128), optimizer, schedule, 4 epochs and seeds as run.sh, and evaluated on all 2,000 test examples. With the official padding:

paperthis reproduction
regular fine-tuning57.29 ± 5.3254.55 ± 6.46
LLM-JEPA (λ = 1)71.46 ± 1.3471.64 ± 2.38

The +17-point gap reproduces, with a similar paired p-value.

What the pipeline actually trains on

Llama's tokenizer has no pad token, so the official code falls back to pad_token = eos_token, which for Llama 3 is <|eot_id|>. DataCollatorForLanguageModeling(mlm=False) then masks every label equal to the pad id. That includes the three genuine <|eot_id|> tokens in each conversation. The model is never trained to end its answer. I checked this by running the official data path on real examples: in the first training example, 74 of 77 tokens are supervised, and the three missing ones are exactly the end-of-turn tokens.

The JEPA embedding positions are not affected: the official code locates the last token with the attention mask, so it picks the same tokens with either pad.

Changing only the pad token to the reserved <|finetune_right_pad_id|> (5 seeds each):

With the end-of-turn token supervised, the paired differences against regular fine-tuning are +0.05, +0.11 and −0.02 points (two-sided p ≥ 0.49). The same holds with assistant-only labels (86.37 vs 86.27).

Why: the regex is right, the model just does not stop

In every condition about 84% of generations start with the exact reference regex. What changes is whether the model stops after it. With a dedicated pad, exact match equals prefix match. With pad = eos, regular fine-tuning often writes the right regex and keeps going, most often appending another .*. For one seed, 554 of its 863 errors are a correct answer followed by extra tokens. LLM-JEPA partly repairs this termination failure, which is where its apparent gain comes from. One plausible but unverified reason: the code-view embedding is taken at the last regex token, the position whose missing target is <|eot_id|>.

Does SIGReg help?

LeJEPA argues that JEPA embeddings should be pushed towards an isotropic Gaussian with SIGReg. I added it to the stacked JEPA embeddings, with its weight chosen on a validation split carved from the training set. It lowers exact match at every λ: −0.3 to −1.1 points with β = 0.001 and −8 to −10 points with β = 0.01. It also makes results more sensitive to λ. In this setting next-token prediction already prevents collapse, so there is nothing for the regularizer to fix.

Limitations

One model, one dataset and five seeds. A single GPU per run instead of 8-GPU DDP, with the same global batch. Batched greedy decoding. This says nothing about LLM-JEPA on other model families: Gemma already has distinct pad and EOS tokens, and the paper reports gains there too. The point is narrower. On Llama, the regular baseline was trained without a stop signal, and that alone accounts for the reported gap on this task.
